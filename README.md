# webinar_mtx

Приложение для управления вебинарами со стримингом через [MediaMTX](https://mediamtx.org):
уникальные комнаты, доступ только для зарегистрированных по email участников,
админка с импортом списков и webhook-интеграциями для авторегистрации после оплаты,
плеер на WebRTC с задержкой меньше секунды.

Написано на Go (один статический бинарник, шаблоны и статика встроены) — весь стек
потребляет ~150–200 МБ RAM в простое.

```
Ведущий (OBS) --RTMP--> MediaMTX --WebRTC/WHEP--> Браузер участника
                            ↑  external auth         ↑  сессия участника
        Приложение (Go + PostgreSQL) ──── админка, комнаты, вебхуки ────
```

## Состав стека

| Компонент | Назначение |
|---|---|
| `app` | Приложение (Go, ~30 МБ RAM): админка, комнаты, вебхуки, WHEP-прокси |
| `db` | PostgreSQL 16 |
| `mediamtx` | Стриминг-сервер: приём RTMP, раздача WebRTC |

## Быстрый старт

```bash
cp .env.example .env
# отредактируйте .env: ADMIN_EMAIL, ADMIN_PASSWORD, APP_SECRET (openssl rand -hex 32),
# MEDIA_HOST — домен или публичный IP сервера
docker compose up -d
```

Админка: `http://localhost:8080/admin` (данные из `ADMIN_EMAIL`/`ADMIN_PASSWORD`).

Порядок первого запуска:

1. **Создайте вебинар** — на странице вебинара появятся RTMP-сервер и
   **ключ потока** для OBS/кодировщика.
2. **Импортируйте участников** (CSV) или добавьте вручную — каждый получит
   персональную ссылку (экспортируйте CSV `email,link` или настройте
   вебхук уведомлений).
3. Установите статус **«В эфире»** и начните трансляцию в OBS — плеер участников
   подхватит эфир автоматически (переподключается сам, пока эфира нет).
4. В админке виден живой счётчик зрителей и статус эфира.

## Доступ участников: персональные ссылки

Вход на вебинар — только по **персональной ссылке** вида
`{APP_URL}/w/{slug}?c={код}`: уникальный код генерируется автоматически при
каждой регистрации (ручное добавление, CSV-импорт, вебхук оплаты). Открывший
ссылку сразу попадает в плеер; без кода комната показывает заглушку.

Доставка ссылок участникам — за пределами приложения, двумя способами:

1. **Исходящий вебхук** `NOTIFY_WEBHOOK_URL`: при каждой новой регистрации
   приложение асинхронно отправляет POST с JSON
   (`event`, `webinar_*`, `email`, `name`, `code`, `link`, `source`).
   Ваша CRM/рассыльщик шлёт письмо с персональной ссылкой. При заданном
   `NOTIFY_WEBHOOK_SECRET` тело подписывается заголовком
   `X-Webhook-Signature: sha256=HMAC-SHA256(тело, секрет)`. Доставка — с
   ретраями и не блокирует регистрацию.
2. **Колбэк публикации записи** `NOTIFY_RECORDING_URL`: когда запись вебинара
   опубликована в S3, каждому активному участнику отправляется событие
   `recording.published` с полями `email`, `name` (ФИО) и
   `recording_url` (+`recording_urls` — все сегменты, если запись не одна).
   Шаблонирование письма и отправку выполняет получатель колбэка. Отдельный
   секрет — `NOTIFY_RECORDING_SECRET` (тот же формат подписи). Заблокированные
   участники событие не получают.
3. **Экспорт CSV** `email,link` со страницы участников (кнопка «Экспорт
   email+ссылки») — для ручной рассылки через CRM. Заблокированные участники
   в экспорт не попадают.

Админ-инструменты: персональная ссылка каждого участника с копированием,
кнопка «Новый код» (старая ссылка мгновенно умирает), блокировка (сбрасывает
активные сессии). Подбор кода затруднён: ~60 бит энтропии и rate-limit
30 попыток/час на IP.

### Запись вебинара и публикация в S3

При настроенном S3-хранилище (переменные `S3_*` в `.env`) вебинары автоматически
записываются и публикуются в бакет:

- MediaMTX пишет запись per-path (приложение включает запись для каждого
  вебинара через Control API; чекбокс «Записывать и публиковать запись»
  позволяет отключить отдельный вебинар);
- после окончания эфира (стрим офлайн ≥10 минут — защита от обрывов — или
  статус «Завершён») воркер загружает сегменты в бакет как
  `{S3_PREFIX}/{recording_id}/{файл}.mp4`, где `recording_id` — случайный
  неподбираемый идентификатор папки;
- ссылка на скачивание автоматически появляется на странице комнаты — **только
  у участников с валидной сессией**; в админке есть кнопки «Копировать» и
  «Опубликовать запись сейчас».

Модель безопасности ссылки: бакет публичный, защита — только знание URL с
неподбираемым идентификатором папки (128 бит энтропии). Ссылка не индексируется
и не показывается без сессии, но тот, кому её переслали, сможет скачать файл.
Публичные ссылки не содержат stream key вещания. При удалении вебинара объекты
в S3 не удаляются.

### Вход в админку через OIDC (SSO)

Админку (и только её — страницы участников не затрагиваются) можно закрыть
корпоративным провайдером: Keycloak, Entra ID (Azure), Google Workspace и
любой другой OIDC-провайдер:

1. В провайдере зарегистрируйте конфиденциальный клиент с redirect URI
   `{APP_URL}/admin/oidc/callback` (Authorization Code flow, PKCE включается
   приложением автоматически).
2. Включите выпуск claim `groups` в ID-токене (в Keycloak — client scope
   `groups` с маппером "Group Membership"; в Dex/Entra ID — соответствующий
   claim-маппинг) и заведите группу для админов.
3. В `.env` задайте `OIDC_ENABLED=true`, `OIDC_ISSUER_URL` (base URL
   провайдера или realm'а), `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` и при
   необходимости `OIDC_ADMIN_GROUP` (название группы, по умолчанию `admin`).

Доступ в админку получают пользователи, у которых в claim `groups`
ID-токена есть группа `OIDC_ADMIN_GROUP` (точное совпадение имени). Кто не в
группе — получает страницу «нет доступа». Email из токена используется только
для отображения в сообщениях и логах.

При включённом OIDC парольный вход полностью отключается; после успешного
входа используется обычная сессия админа (cookie). Переменные
`ADMIN_EMAIL`/`ADMIN_PASSWORD` остаются обязательными — это логин и пароль
для входа без OIDC.

Как защищён стрим:

- путь потока в MediaMTX — `w/{случайный ключ}`, подобрать его невозможно;
- каждая публикация и каждое чтение проходят через **external authentication**
  MediaMTX → приложение сверяет ключ вебинара / токен сессии участника;
- сигналинг WHEP идёт через приложение (проверка сессии), а видео летит напрямую
  браузер ↔ MediaMTX — приложение не тратит ресурсы на трафик.

## Вебхуки (авторегистрация после оплаты)

Админка → «Вебхуки» → создать. Для приёма платежей настраиваются:

- **URL** — `https://ваш-домен/hooks/{id}` + секрет в заголовке `X-Webhook-Secret`
  (или параметр `?secret=`);
- **пути к полям** в JSON-уведомлении: где искать email клиента и id товара/тарифа
  (dot-нотация, например `object.metadata.email`);
- **маппинг** `id_товара = slug_вебинара` — какому вебинару соответствует товар;
- необязательный **вебинар по умолчанию**, если товар в маппинге не найден.

Есть пресеты полей для ЮKassa, CloudPayments, Stripe, Prodamus и Т-Банка и кнопка
«тестовый запрос». Повторные уведомления идемпотентны. Поддерживаются JSON и
`form-urlencoded`. Необязательное поле `name` в payload сохраняется как ФИО
участника.

Готовый сценарий регистрации с **Google Форм** (форма → Apps Script → вебхук →
письмо с персональной ссылкой) — в [docs/google-forms-integration.md](docs/google-forms-integration.md).

Пример (ЮKassa-подобный payload):

```bash
curl -X POST https://домен/hooks/wh_xxx \
  -H "X-Webhook-Secret: whsec_..." \
  -H "Content-Type: application/json" \
  -d '{"object":{"metadata":{"email":"client@example.com","product":"webinar-pro"}}}'
```

## Переменные окружения

Все переменные со значениями и комментариями — в [`.env.example`](.env.example).

Ключевые: `APP_URL` (публичный адрес, используется в ссылках и письмах),
`MEDIA_HOST` (публичный адрес для ICE-кандидатов WebRTC — без него браузеры за NAT
не подключатся), `RTMP_URL` (адрес RTMP, показываемый ведущему), `APP_SECRET`.

### Что такое APP_SECRET

`APP_SECRET` — симметричный ключ (HMAC), которым приложение подписывает все
cookie-сессии: сессию админа, сессии участников в комнатах вебинаров и
OIDC state-cookie. Подпись гарантирует, что cookie нельзя подделать: сервер
проверяет её при каждом запросе, а содержимое сессий (кто участник какого
вебинара) при этом лежит в PostgreSQL.

Как заполнять:

```bash
openssl rand -hex 32      # вставьте вывод в APP_SECRET=
```

- один и тот же ключ на всех рестартах/деплоях → участники не вылетают
  с вебинара при обновлении приложения;
- смена ключа → мгновенно аннулирует все сессии (админов и участников);
- пустое значение → при каждом старте генерируется временный ключ, и после
  любого рестарта контейнера всем придётся входить заново — только для
  локальных экспериментов;
- держите значение в секрете: тот, кто знает ключ, может подделать
  админскую сессию.

## Порты

| Порт | Назначение |
|---|---|
| 8080/tcp | Приложение (админка + комнаты + WHEP-прокси) |
| 1935/tcp | RTMP: приём трансляции (OBS) |
| 8889/tcp | WHEP-сигналинг MediaMTX |
| 8189/tcp+udp | ICE: медиа-трафик WebRTC |

UDP 8189 даёт минимальную задержку; TCP 8189 — запасной путь для сетей с
блокировкой UDP. Для лучшей задержки на Linux можно запускать mediamtx с
`network_mode: host`.

## Сборка и публикация контейнера

- **Dockerfile** — multi-stage сборка, итоговый образ на distroless/static ~20 МБ.
- `.github/workflows/release.yml` на каждый push в `main` и теги `v*`: тесты →
  сборка multi-arch (amd64+arm64) → публикация:
  - **GHCR** `ghcr.io/vdao/webinar_mtx` — всегда (dev-сборки `main`: теги
    `latest` и sha; релизные теги: `X.Y.Z`, `X.Y`, sha). Аутентификация через
    встроенный `GITHUB_TOKEN` — секреты не нужны.
  - **Docker Hub** `docker.io/<неймспейс>/webinar_mtx` — только официальные
    релизы (теги `v*`): теги `X.Y.Z`, `X.Y` и `latest` (всегда последний
    стабильный релиз, dev-сборки `main` туда не попадают).

### Включение публикации на Docker Hub

1. На hub.docker.com создайте Personal Access Token с правами Read/Write
   (Account Settings → Personal access tokens). Репозиторий `webinar_mtx`
   создастся автоматически при первом пуше в вашем неймспейсе.
2. В настройках репозитория (Settings → Secrets and variables → Actions):

| Где | Имя | Значение |
|---|---|---|
| Variables | `DOCKERHUB_NAMESPACE` | ваш пользователь или организация на Docker Hub (без переменной публикация туда просто пропускается) |
| Secrets | `DOCKERHUB_USERNAME` | имя пользователя Docker Hub для входа |
| Secrets | `DOCKERHUB_TOKEN` | Personal Access Token |

3. Выпустите релиз — пуш тега запускает официальный паблиш:

```bash
git tag v0.3.0
git push origin v0.3.0
```

После этого образ доступен как `docker.io/<неймспейс>/webinar_mtx:0.3.0`
(а также `:0.3` и `:latest`). Если хотите, чтобы `docker-compose.yml` тянул
образ с Docker Hub — поменяйте `image:` у сервиса `app`.

## Развёртывание в Coolify

Для Coolify используйте [`deploy/coolify/docker-compose.yml`](deploy/coolify/docker-compose.yml):
приложение за доменом/HTTPS прокси Coolify, MediaMTX настраивается переменными
`MTX_*` без файлов. Пошаговое руководство — [docs/coolify.md](docs/coolify.md).

## Развёртывание на сервере

`docker-compose.yml` из репозитория готов к использованию как основа деплоя
(его же использует `deploy.yml`). Чек-лист прода:

1. На сервере: каталог (по умолчанию `/opt/webinar_mtx`) с файлами
   `docker-compose.yml`, `.env`, `mediamtx/mediamtx.yml` из репозитория.
2. В `.env` заполнить: `APP_TAG` (пинуйте релиз, напр. `0.0.2`),
   `ADMIN_EMAIL`/`ADMIN_PASSWORD`, `APP_SECRET` (`openssl rand -hex 32`),
   пароли `POSTGRES_*`, `APP_URL` и `RTMP_URL` с доменом сервера,
   `MEDIA_HOST` — домен/IP сервера (без него WebRTC за NAT не подключится).
3. Reverse-proxy с TLS (Caddy/Traefik/nginx): `https://вебинар.домен` →
   `app:8080`.
4. Firewall: наружу нужны `8080` (или 443 на прокси), `1935` (RTMP для
   ведущего), `8189/tcp+udp` (медиа WebRTC). Порт `8889` наружу не обязателен
   — сигналинг WHEP идёт через приложение.
5. `docker compose pull && docker compose up -d` — миграции применятся сами.
6. Бэкапы: `pg_dump` тома `pgdata` (записи в S3, локальный том записей —
   временный).

## Автодеплой

`.github/workflows/deploy.yml` деплоит по SSH при публикации тега `v*` (или вручную):
`docker compose pull && docker compose up -d` на сервере.

Настройка (Settings → Secrets and variables → Actions):

| Где | Имя | Значение |
|---|---|---|
| Variables | `DEPLOY_HOST` | адрес сервера (без переменной деплой просто пропускается) |
| Secrets | `DEPLOY_USER` | SSH-пользователь (по умолчанию `root`) |
| Secrets | `DEPLOY_KEY` | приватный SSH-ключ |
| Secrets | `DEPLOY_PATH` | каталог с `docker-compose.yml` (по умолчанию `/opt/webinar_mtx`) |

На сервере в каталоге должны лежать `docker-compose.yml`, `.env`
и `mediamtx/mediamtx.yml` из этого репозитория.

## Производство: HTTPS

Для продакшена поставьте reverse-proxy с TLS (Caddy/Traefik/nginx) перед приложением:
`https://вебинар.домен` → `app:8080`. WHEP-плеер работает и по HTTP, но HTTPS
и просто правильный тон для страниц с входом.

## Разработка

```bash
go test ./...        # юнит-тесты
go vet ./...
docker compose up    # локальный стек: приложение + postgres + mediamtx
```

Тестовый поток без OBS:

```bash
docker run --rm --network webinar_mtx_default --entrypoint ffmpeg \
  bluenviron/mediamtx:1.21.3-ffmpeg \
  -re -f lavfi -i testsrc2=size=1280x720:rate=30 -f lavfi -i sine=frequency=440 \
  -c:v libx264 -preset veryfast -tune zerolatency -c:a aac -f flv \
  rtmp://mediamtx:1935/w/КЛЮЧ_ПОТОКА
```

Структура кода:

```
cmd/server          точка входа
internal/config     переменные окружения
internal/db         подключение и миграции (embedded SQL)
internal/store      все SQL-запросы
internal/model      сущности
internal/web        HTTP-хендлеры: админка, комнаты, WHEP-прокси, вебхуки, external auth, OIDC
internal/recorder   воркер публикации записей в S3 (детект конца эфира, загрузка, ретраи)
internal/s3         клиент S3-хранилища (minio-go)
internal/oidc       OIDC-вход для админки (Authorization Code + PKCE)
internal/mtx        клиент REST API MediaMTX (счётчик зрителей, управление записью путей)
internal/web/notify.go  исходящий вебхук уведомлений о регистрациях
internal/csvutil    парсер CSV-импорта
internal/auth       сессия админа, cookie участников, rate limiter
web → internal/web/{templates,static}  встроенные шаблоны и статика
```
